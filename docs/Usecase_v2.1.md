# 어노잉 레이더 — Usecase v2.1

## 0. 문서 목적

이 문서는 **어노잉 레이더**의 초기 구현 범위를 유즈케이스 중심으로 정의한다.

v2.1에서는 이전 문서의 보완사항을 실제 문서 구조에 반영했다.

- 프로젝트명은 **어노잉 레이더**로 통일한다.
- 첫 사용 흐름은 `프로젝트 생성`이 아니라 `텍스트 입력 → 분석 → 문제 후보 확인 → 문제 카드 확정`으로 시작한다.
- v0.1은 관리 기능보다 **문제 카드 생성 경험**에 집중한다.
- `Problem Candidate`와 `Problem Card`의 경계를 명확히 한다.
- 분석 상태값을 별도 상태머신으로 정의한다.
- 최근 분석 목록은 전체 히스토리 관리가 아니라 **최근 3개 빠른 재진입**으로 제한한다.
- 초기 지표는 `근거 수 / 감정 강도 / 반복 패턴 / 문제 명확도`로 제한한다.
- `구현 난이도`는 v0.2의 아이디어 후보화 단계에서 다룬다.

이 문서는 이후 `Sequence.md → Class.md → Logic.md` 설계의 기준 문서로 사용한다.

---

## 1. 프로젝트 한 줄 정의

> **어노잉 레이더는 사용자가 붙여넣은 불만 텍스트에서 반복되는 문제를 추출하고, 실제 근거가 붙은 문제 카드로 정리해주는 개인용 문제 발굴 엔진이다.**

---

## 2. 프로젝트 정체성

### 2.1 어노잉 레이더가 하는 일

어노잉 레이더는 인터넷 전체를 자동으로 뒤지는 플랫폼이 아니다.

초기 구현의 핵심은 다음이다.

```text
사용자가 원문 텍스트를 붙여넣는다
→ 시스템이 불만 문장을 추출한다
→ 사용자가 추출 결과를 검토한다
→ 시스템이 유사 불만을 문제 후보로 묶는다
→ 사용자가 문제 후보를 검토한다
→ 사용자가 의미 있는 후보만 문제 카드로 확정한다
```

---

### 2.2 어노잉 레이더가 하지 않는 일

초기 구현에서는 다음을 하지 않는다.

- 실시간 크롤링
- 전체 인터넷 자동 탐색
- 자체 AI 모델 학습
- 완전 자동 시장성 판정
- 단일 종합 점수로 아이디어 순위 매기기
- 문제 근거 없는 아이디어 생성
- 프로젝트 관리 도구 중심의 무거운 UX
- 사용자가 검토하지 않은 AI 결과를 최종 문제 카드로 확정하기

---

## 3. 핵심 원칙

### 3.1 첫 경험은 “텍스트 넣으면 문제 후보가 나온다”여야 한다

사용자가 처음 해야 할 일은 프로젝트명 입력이 아니다.

첫 화면은 다음 행동을 유도해야 한다.

```text
불편함이 담긴 글, 리뷰, 댓글을 붙여넣으세요.
```

사용자가 원문을 넣고 분석했을 때 곧바로 다음 결과를 봐야 한다.

- 추출된 불만 문장
- 반복되는 문제 후보
- 근거가 붙은 문제 후보 카드

---

### 3.2 중심 객체는 AI 답변이 아니라 Problem Card다

어노잉 레이더의 핵심 산출물은 채팅 응답이 아니다.

핵심 산출물은 사용자가 확정한 **Problem Card**다.

```text
Problem Card
- 문제 제목
- 문제 요약
- 대상 사용자
- 발생 상황
- 대표 근거
- 근거 수
- 감정 강도
- 반복 패턴
- 문제 명확도
```

---

### 3.3 근거 없는 문제 카드는 만들지 않는다

모든 Problem Card는 반드시 하나 이상의 실제 근거를 가져야 한다.

근거 없는 아이디어나 문제 설명은 어노잉 레이더의 핵심 산출물이 아니다.

```text
Raw Input
→ Pain Evidence
→ Problem Candidate
→ Confirmed Problem Card
```

---

### 3.4 AI는 초안을 만들고, 사용자가 확정한다

AI가 자동으로 추출하고 묶더라도 최종 확정자는 사용자다.

사용자 검토가 필요한 단계는 다음이다.

- 불만 문장 삭제/수정
- 잘못 묶인 문제 분리
- 비슷한 문제 병합
- 문제 후보 제목 수정
- 문제 후보 요약 수정
- 최종 문제 카드 확정
- 불필요한 후보 폐기

---

### 3.5 지표는 최소 단위부터 시작한다

초기 구현에서는 지표를 과하게 늘리지 않는다.

v0.1에서는 다음 4개 지표만 사용한다.

| 지표 | 목적 |
|---|---|
| 근거 수 | 실제 반복 근거가 충분한지 확인 |
| 감정 강도 | 사용자의 불만이 얼마나 강한지 확인 |
| 반복 패턴 | 유사한 불만이 얼마나 비슷하게 반복되는지 확인 |
| 문제 명확도 | 이 문제가 하나의 명확한 문제로 정의될 수 있는지 확인 |

후속 단계에서 아래 지표를 추가한다.

- 구현 난이도
- 최근성
- 해결 공백
- 수익화 가능성
- 내 역량 적합도
- 경쟁 서비스 존재 여부

## 6. 핵심 도메인 용어

| 용어 | 정의 |
|---|---|
| Raw Input | 사용자가 붙여넣은 원문 텍스트 묶음 |
| Source Info | 출처 유형, URL, 메모 |
| Pain Evidence | 원문에서 추출된 불만/문제/개선 요구 문장 |
| Evidence Review | 사용자가 AI 추출 결과를 검토하고 확정하는 단계 |
| Problem Candidate | AI가 유사 Evidence를 묶어 만든 문제 후보 초안 |
| Problem Card | 사용자가 Problem Candidate를 검토 후 직접 확정한 문제 결과물 |
| Problem Metric | 근거 수, 감정 강도, 반복 패턴, 문제 명확도 등 문제 판단 지표 |
| Idea Candidate | Problem Card에서 파생된 서비스 아이디어 후보 |
| Idea Board | 후속 단계에서 아이디어 후보를 상태별로 관리하는 보드 |
| Report | 후속 단계에서 문제와 아이디어를 문서화한 마크다운 리포트 |

### 6.1 Problem Candidate와 Problem Card의 구분

`Problem Candidate`와 `Problem Card`는 같은 의미가 아니다.

```text
Problem Candidate = AI가 만든 문제 후보 초안
Problem Card = 사용자가 직접 확정한 문제 결과물
```

초기 구현에서는 별도 테이블을 분리하지 않고, `Problem Candidate`의 `status` 값으로 구분할 수 있다.

```text
draft      = AI가 생성한 문제 후보 초안
confirmed  = 사용자가 확정한 Problem Card
discarded  = 사용자가 폐기한 문제 후보
```

규칙:

- `status = confirmed`인 Problem Candidate만 UI에서 Problem Card로 취급한다.
- `draft` 상태는 저장된 문제 카드가 아니다.
- `discarded` 상태는 기본 목록에서 숨긴다.
- 확정되지 않은 Candidate에서는 Idea Candidate를 생성하지 않는다.
- 사용자가 직접 확정하지 않은 문제는 어노잉 레이더의 최종 산출물로 보지 않는다.

## 7. 분석 상태머신

분석 상태는 `Raw Input` 기준으로 관리한다.

### 7.1 analysis_status 값

```text
idle
input_saved
extracting
extraction_failed
reviewing_evidence
grouping
grouping_failed
reviewing_candidates
completed
```

| 상태 | 의미 |
|---|---|
| idle | 아직 입력이 시작되지 않은 상태 |
| input_saved | 원문 입력이 저장된 상태 |
| extracting | 불만 문장 추출 중 |
| extraction_failed | 불만 문장 추출 실패 |
| reviewing_evidence | 추출 결과 검토 중 |
| grouping | 유사 불만 묶기 진행 중 |
| grouping_failed | 문제 후보 묶기 실패 |
| reviewing_candidates | 문제 후보 검토 중 |
| completed | 문제 후보 확정/폐기까지 완료된 상태 |

### 7.2 상태 전이

```text
idle
→ input_saved
→ extracting
→ reviewing_evidence
→ grouping
→ reviewing_candidates
→ completed
```

실패 흐름:

```text
extracting
→ extraction_failed
→ extracting

grouping
→ grouping_failed
→ grouping
```

규칙:

- 사용자가 원문을 입력하면 `input_saved`가 된다.
- 사용자가 분석을 시작하면 `extracting`이 된다.
- 불만 문장 추출이 완료되면 `reviewing_evidence`가 된다.
- 사용자가 Evidence를 확정하고 문제 묶기를 실행하면 `grouping`이 된다.
- 문제 후보 생성이 완료되면 `reviewing_candidates`가 된다.
- 사용자가 후보를 확정하거나 폐기하면 `completed`가 된다.
- 실패 상태에서는 재시도 버튼을 제공한다.
- 실패해도 Raw Input과 기존 Evidence는 삭제하지 않는다.

# 9. 상세 유즈케이스

## UC-01. 원문 텍스트 입력

### 목적

사용자가 분석하고 싶은 불만 텍스트를 가장 빠르게 입력한다.

### 액터

- 사용자

### 사전 조건

- 사용자가 어노잉 레이더에 접속해 있다.

### 트리거

- 사용자가 첫 화면의 입력 영역에 텍스트를 붙여넣는다.

### 기본 흐름

1. 사용자가 원문 텍스트를 붙여넣는다.
2. 사용자가 원문 유형을 선택한다.
   - Reddit
   - App Review
   - G2/Capterra Review
   - Product Hunt
   - Naver Cafe
   - DCInside
   - Community
   - 기타
3. 사용자가 선택적으로 URL 또는 출처 메모를 입력한다.
4. 사용자가 “분석 시작” 버튼을 누른다.
5. 시스템은 Raw Input을 임시 저장한다.
6. 시스템은 `analysis_status = input_saved`로 변경한다.
7. 시스템은 불만 문장 추출을 시작하며 `analysis_status = extracting`으로 변경한다.

### 대체 흐름

- 텍스트가 너무 짧으면 시스템은 “분석에 충분하지 않을 수 있음” 경고를 표시한다.
- 텍스트가 너무 길면 시스템은 분할 분석 안내를 표시한다.
- URL이 없어도 분석 가능하다.
- 사용자가 출처 유형을 고르지 않으면 기본값은 “기타”다.

### 결과

- Raw Input이 생성된다.
- 분석 상태가 `extracting`으로 변경된다.

### 수용 기준

- 사용자는 프로젝트 생성 없이 바로 텍스트를 입력할 수 있어야 한다.
- 입력된 원문은 분석 전까지 수정 가능해야 한다.
- 같은 텍스트를 반복 입력하면 시스템은 중복 가능성을 경고한다.
- 분석 시작 전에는 `input_saved`, 분석 시작 후에는 `extracting` 상태가 되어야 한다.

### 우선순위

## UC-03. 불만 문장 추출

### 목적

원문 텍스트에서 불만, 문제, 개선 요구, 반복되는 귀찮음, 대안 요청 문장을 추출한다.

### 액터

- 사용자
- 시스템
- AI 분석기

### 사전 조건

- Raw Input이 존재한다.
- `analysis_status = extracting` 상태다.

### 트리거

- 시스템이 Raw Input 분석을 시작한다.

### 기본 흐름

1. 시스템은 Raw Input을 분석 가능한 단위로 나눈다.
2. AI 분석기는 각 단위에서 불만 후보 문장을 추출한다.
3. 시스템은 추출된 문장을 Pain Evidence로 저장한다.
4. 각 Pain Evidence에는 다음 정보를 붙인다.
   - 원문 문장
   - 한국어 요약
   - 불만 유형
   - 대상 사용자
   - 발생 상황
   - 감정 강도
   - 출처 정보
5. 시스템은 `analysis_status = reviewing_evidence`로 변경한다.
6. 시스템은 추출 결과 검토 화면으로 이동한다.

### 추출 대상

- 불편함
- 짜증
- 반복되는 귀찮음
- 이해하기 어려움
- 시간이 오래 걸림
- 돈 낭비
- 수동 반복 작업
- 기존 도구 불만
- 대안 요청
- 해결되지 않은 니즈
- “wish”, “hate”, “annoying”, “frustrating” 계열 표현

### 제외 대상

- 단순 칭찬
- 광고 문구
- 정보성 문장
- 농담
- 맥락 없는 욕설
- 출처 불명확한 주장
- 해결책만 있고 문제가 없는 문장

### 대체 흐름

- AI 분석 실패 시 `analysis_status = extraction_failed`로 변경한다.
- 추출 결과가 적으면 “명확한 불만이 적음” 상태를 표시한다.
- 추출 결과가 너무 많으면 감정 강도와 중복도를 기준으로 우선순위를 붙인다.

### 결과

- Pain Evidence 목록이 생성된다.
- 분석 상태가 `reviewing_evidence`가 된다.

### 수용 기준

- AI가 생성한 요약과 실제 원문 문장은 분리 저장되어야 한다.
- 모든 Evidence는 원문 위치 또는 원문 일부와 연결되어야 한다.
- 추출된 Evidence는 사용자 확정 전까지 `draft` 상태다.
- 추출 실패 시 원문은 삭제되지 않아야 한다.

### 우선순위

P0

## UC-04. 추출 결과 검토/편집

### 목적

AI 추출 결과의 품질을 사용자가 직접 보정한다.

### 액터

- 사용자

### 사전 조건

- Pain Evidence 초안이 생성되어 있다.
- `analysis_status = reviewing_evidence` 상태다.

### 트리거

- 시스템이 추출 결과 검토 화면을 표시한다.

### 기본 흐름

1. 사용자는 Pain Evidence 목록을 확인한다.
2. 사용자는 부정확한 Evidence를 삭제한다.
3. 사용자는 요약 문구를 수정한다.
4. 사용자는 감정 강도를 수정한다.
5. 사용자는 불만 유형을 수정한다.
6. 사용자는 확정할 Evidence를 선택한다.
7. 사용자가 “확정 후 문제 묶기”를 누른다.
8. 시스템은 선택된 Evidence만 `confirmed` 상태로 변경한다.
9. 시스템은 `analysis_status = grouping`으로 변경한다.

### 대체 흐름

- 사용자는 전체 항목을 한 번에 확정할 수 있다.
- 사용자는 일부 항목만 확정할 수 있다.
- 사용자는 전체 재분석을 요청할 수 있다.
- 사용자는 원문을 수정한 뒤 다시 분석할 수 있다.
- 확정할 Evidence가 없으면 문제 묶기로 넘어갈 수 없다.

### 결과

- 확정된 Pain Evidence가 생성된다.
- 분석 상태가 `grouping`이 된다.

### 수용 기준

- 삭제된 Evidence는 기본 문제 묶기에서 제외된다.
- 사용자가 수정한 값은 AI 초안보다 우선한다.
- 확정 전/후 상태가 명확히 구분되어야 한다.
- confirmed 상태의 Evidence만 문제 묶기에 사용해야 한다.

### 우선순위

## UC-05. 유사 불만 묶기

### 목적

확정된 Pain Evidence를 유사 문제 단위로 묶는다.

### 액터

- 사용자
- 시스템
- AI 분석기

### 사전 조건

- 확정된 Pain Evidence가 1개 이상 존재한다.
- `analysis_status = grouping` 상태다.

### 트리거

- 사용자가 “확정 후 문제 묶기”를 누른 뒤 시스템이 묶기를 시작한다.

### 기본 흐름

1. 시스템은 확정된 Pain Evidence를 AI 분석기에 전달한다.
2. AI 분석기는 유사 Evidence를 Problem Candidate로 묶는다.
3. 시스템은 각 Problem Candidate에 임시 제목과 요약을 생성한다.
4. 시스템은 각 Problem Candidate를 `draft` 상태로 저장한다.
5. 시스템은 `analysis_status = reviewing_candidates`로 변경한다.
6. 시스템은 문제 묶기 검토 화면을 표시한다.

### 묶기 기준

- 같은 사용자가 겪는 문제인가
- 같은 상황에서 발생하는가
- 같은 행동 흐름에서 발생하는가
- 같은 해결책으로 접근 가능한가
- 표현만 다르고 본질이 같은가

### 대체 흐름

- Evidence가 적으면 시스템은 단일 Problem Candidate를 생성할 수 있다.
- 사용자가 수동으로 새 문제 후보를 만들 수 있다.
- 사용자가 특정 Evidence를 다른 후보로 이동할 수 있다.
- 묶기 실패 시 `analysis_status = grouping_failed`로 변경한다.

### 결과

- Problem Candidate 목록이 생성된다.
- 분석 상태가 `reviewing_candidates`가 된다.

### 수용 기준

- 완전 자동 확정은 하지 않는다.
- 사용자가 병합/분리/삭제할 수 있어야 한다.
- 하나의 Problem Candidate는 최소 1개 이상의 Evidence를 가져야 한다.
- 확정된 Problem Card와 폐기된 Candidate를 구분해야 한다.

### 우선순위

## UC-06. 문제 후보 카드 조회

### 목적

사용자가 AI가 묶은 문제 후보를 카드 형태로 빠르게 비교한다.

### 액터

- 사용자

### 사전 조건

- Problem Candidate가 생성되어 있다.
- `analysis_status = reviewing_candidates` 상태다.

### 트리거

- 사용자가 문제 묶기 결과 화면에 진입한다.

### 기본 흐름

1. 시스템은 Problem Candidate를 카드 목록으로 표시한다.
2. 각 카드에는 다음 정보를 보여준다.
   - 문제 제목
   - 짧은 요약
   - 대상 사용자
   - 대표 상황
   - 근거 수
   - 감정 강도
   - 반복 패턴
   - 문제 명확도
3. 사용자는 카드를 열어 상세를 확인한다.
4. 사용자는 카드를 확정하거나 폐기한다.

### 정렬 기준

초기 구현에서는 최소 정렬만 제공한다.

- 근거 많은 순
- 감정 강도 높은 순
- 최근 생성 순

### 대체 흐름

- 카드가 없으면 “유의미한 문제 후보 없음” 상태를 표시한다.
- 근거가 1개뿐인 카드는 `근거 부족` 배지를 표시한다.
- 사용자는 카드 제목을 바로 수정할 수 있다.

### 결과

- 사용자가 문제 후보를 빠르게 검토할 수 있다.

### 수용 기준

- 카드 한 장만 봐도 어떤 문제인지 이해되어야 한다.
- 원문 게시글 목록처럼 보이면 안 된다.
- 각 카드는 반드시 근거 수를 표시해야 한다.
- 확정 전 카드는 `Problem Candidate`, 확정 후 카드는 `Problem Card`로 구분한다.

### 우선순위

## UC-07. 문제 후보 상세 조회

### 목적

사용자가 특정 문제 후보의 근거와 맥락을 깊게 확인한다.

### 액터

- 사용자

### 사전 조건

- Problem Candidate 또는 Problem Card가 존재한다.

### 트리거

- 사용자가 문제 후보 카드를 클릭한다.

### 기본 흐름

1. 시스템은 문제 후보 상세 화면을 연다.
2. 화면 상단에는 문제 제목과 요약을 표시한다.
3. 중간 영역에는 4개 핵심 지표를 표시한다.
   - 근거 수
   - 감정 강도
   - 반복 패턴
   - 문제 명확도
4. 하단에는 Evidence 목록을 표시한다.
5. 사용자는 각 Evidence의 원문, 요약, 출처를 확인한다.
6. 사용자는 문제 제목과 요약을 수정한다.
7. 사용자는 Evidence를 제거하거나 다른 문제 후보로 이동한다.
8. 사용자는 문제 후보를 확정하거나 폐기한다.

### 상세 화면 구성

```text
문제 제목
문제 요약
대상 사용자
발생 상황
4개 핵심 지표
대표 근거
전체 Evidence 목록
Evidence 이동/제거
확정 버튼
폐기 버튼
```

### 대체 흐름

- 출처 URL이 없으면 출처 메모만 표시한다.
- Evidence가 1개뿐이면 `근거 부족` 표시를 붙인다.
- 문제 명확도를 판단할 수 없으면 `판단 보류`로 표시한다.

### 결과

- 사용자가 문제 후보의 신뢰도와 활용 가능성을 판단한다.

### 수용 기준

- AI 요약과 실제 근거 문장이 명확히 구분되어야 한다.
- 문제 상세 화면에는 원문 근거가 반드시 보여야 한다.
- 사용자는 문제를 확정하거나 폐기할 수 있어야 한다.
- 확정 전에는 Idea Candidate 생성 버튼을 노출하지 않는다.

### 우선순위

## UC-08. 문제 카드 확정/폐기

### 목적

사용자가 AI가 만든 문제 후보 중 의미 있는 것만 확정한다.

### 액터

- 사용자

### 사전 조건

- Problem Candidate가 존재한다.
- `analysis_status = reviewing_candidates` 상태다.

### 트리거

- 사용자가 문제 후보에서 `확정` 또는 `폐기`를 선택한다.

### 기본 흐름

1. 사용자가 Problem Candidate를 검토한다.
2. 사용자가 제목, 요약, Evidence를 수정한다.
3. 사용자가 `문제 카드로 확정`을 누른다.
4. 시스템은 해당 Candidate의 `status`를 `confirmed`로 변경한다.
5. 사용자가 불필요한 Candidate는 `폐기`한다.
6. 시스템은 폐기된 Candidate의 `status`를 `discarded`로 변경한다.
7. 모든 후보 처리가 끝나면 시스템은 `analysis_status = completed`로 변경한다.

### 대체 흐름

- 사용자는 확정 전에 추가 Evidence를 붙일 수 있다.
- 사용자는 폐기 사유를 선택적으로 입력할 수 있다.
- 폐기한 Candidate는 복구할 수 있다.
- 일부 후보만 확정하고 나머지는 draft로 남길 수 있다.

### 결과

- 확정된 Problem Card와 폐기된 Candidate가 구분된다.
- 분석 상태가 필요 시 `completed`가 된다.

### 수용 기준

- 확정된 카드만 v0.2의 아이디어 후보화 대상으로 사용할 수 있다.
- 폐기된 후보는 완전 삭제하지 않는다.
- 사용자가 직접 확정하지 않은 문제는 저장된 문제 카드로 취급하지 않는다.
- `status = confirmed`인 Candidate만 Problem Card로 표시한다.

### 우선순위

P0

## 11. v0.1 사용자 시나리오

### 시나리오 A. 프리랜서 정산 문제 발굴

```text
1. 사용자는 프리랜서 정산 관련 Reddit 글과 댓글을 복사한다.
2. 어노잉 레이더 첫 화면에 원문 텍스트를 붙여넣는다.

4. 분석 시작을 누른다.
5. 시스템은 불만 문장을 추출한다.
6. 사용자는 추출 결과에서 부정확한 항목을 삭제한다.
7. 사용자는 의미 있는 Evidence만 확정한다.
8. 시스템은 유사 Evidence를 문제 후보로 묶는다.
9. 사용자는 "프리랜서가 미납 고객에게 결제 요청을 반복하기 어렵다" 후보를 연다.
10. 사용자는 근거 문장과 감정 강도를 확인한다.
11. 사용자는 문제 제목을 수정한다.
12. 사용자는 문제 카드로 확정한다.
```

---

### 시나리오 B. 비주얼리 개선 리서치

```text
1. 사용자는 화장품 추천 앱, 리뷰 앱, 스킨케어 커뮤니티의 불만 글을 복사한다.

7. 시스템은 이를 문제 후보로 묶는다.
8. 사용자는 "추천 이유의 신뢰 부족" 문제 후보를 연다.
```

```text
6. 사용자는 두 후보의 제목과 요약을 각각 수정한다.

```

## 12. 화면 단위 요구사항

### 12.1 Input First Page

#### 목적

사용자가 프로젝트 생성 없이 바로 분석을 시작한다.

#### 주요 요소

- 큰 텍스트 입력 영역
- 출처 유형 선택
- URL 입력
- 출처 메모
- 분석 시작 버튼
- 최근 3개 분석 빠른 재진입

#### 최근 분석 표시 기준

v0.1에서는 전체 히스토리 관리 기능을 제공하지 않는다.

- 검색, 필터, 전체 히스토리 관리는 v0.2 이후로 미룬다.
- 프로젝트 단위 관리는 저장 단계 이후에 연결한다.

#### 핵심 문구

```text
불편함이 담긴 글, 리뷰, 댓글을 붙여넣으세요.
```

## 14. 핵심 비기능 요구사항

### 14.1 신뢰성

- AI 결과는 항상 원문 근거와 연결되어야 한다.
- 근거 없는 문제 카드는 확정할 수 없다.
- 출처 없는 근거는 신뢰 낮음으로 표시한다.
- 사용자가 AI 결과를 수정할 수 있어야 한다.

---

### 14.2 속도

- 대용량 실시간 분석을 목표로 하지 않는다.
- 분석은 단계별 진행 상태를 보여준다.
- 긴 텍스트는 분할 분석한다.
- 실패 시 전체 작업이 날아가지 않아야 한다.

---

### 14.3 비용

- 같은 Raw Input을 중복 분석하지 않는다.
- 재분석 시 기존 Evidence를 재사용할 수 있어야 한다.
- 너무 긴 입력은 분할 전 사용자에게 안내한다.
- 불필요한 재분석 버튼 남발을 막는다.

---

### 14.4 확장성

- 자동 수집을 나중에 붙일 수 있도록 Raw Input과 Source Info를 분리한다.
- 프로젝트 관리는 후속 단계에서 연결 가능하게 한다.
- Problem Card 구조는 입력 방식이 바뀌어도 유지한다.

---

### 14.5 개인정보/정책

- 개인 식별 정보는 저장하지 않는 것을 기본값으로 한다.
- 작성자명은 저장하지 않거나 해시 처리한다.
- 비공개 커뮤니티, 로그인 필요 콘텐츠, 유료 콘텐츠 자동 수집은 하지 않는다.
- 외부 원문은 가능한 요약과 짧은 근거 중심으로 관리한다.
- 사용자가 붙여넣은 원문에 개인정보가 포함될 수 있음을 안내한다.

---

## 15. v0.1 성공 기준

v0.1은 다음이 가능하면 성공으로 본다.

```text
1. 사용자가 프로젝트 생성 없이 원문 텍스트를 붙여넣는다.
2. 시스템이 불만 문장을 추출한다.
3. 사용자가 추출 결과를 검토하고 확정한다.
4. 시스템이 확정 Evidence를 문제 후보로 묶는다.
5. 사용자가 잘못 묶인 후보를 수정한다.
6. 사용자가 문제 상세에서 근거 원문을 확인한다.
7. 사용자가 문제 후보를 확정하거나 폐기한다.
8. confirmed 상태의 Problem Candidate만 Problem Card로 취급된다.
9. 확정된 문제 카드만 다음 단계의 아이디어 후보화 대상으로 남는다.
```
