# Phase 15.4 — Threads Source Spike / Source Adapter

## Status

Implementation target: official Threads public-post keyword search → normalized Source Signal ingestion.

This phase does **not** classify complaints and does **not** create Public Problems.

## Why this phase exists

Public Radar now has an Explore surface and a curator publication workflow, but it still lacks an external supply path. Phase 15.4 introduces the first real Source Adapter while preserving the rule that external content is only raw observational material.

```text
Threads public search
        ↓
Source Adapter
        ↓
Source Signal
        ↓
Observation / provenance
        ↓
(next phase) Complaint filtering
        ↓
Evidence / Problem pipeline
```

## Official API basis

As verified on 2026-08-18 against Meta's official Threads Postman workspace:

- host: `https://graph.threads.net`
- endpoint: `GET /keyword_search`
- permission/scope: `threads_keyword_search`
- `search_type`: `TOP` or `RECENT`
- `search_mode`: `KEYWORD` or `TAG`
- supported request dimensions include `q`, `limit`, `since`, `until`, and `fields`
- fields used by this adapter: `id`, `media_type`, `permalink`, `username`, `text`, `timestamp`, `shortcode`, `is_quote_post`, `has_replies`

The access token is server-only and sent through OAuth Bearer authorization. It is never embedded in a browser response or request URL generated by the adapter.

## Data model

### `ar_source_ingestion_runs`

One external search execution.

Stores:
- platform
- query
- search type/mode
- since/until window
- requested limit
- status
- fetched/new/duplicate/skipped counts
- curator who initiated the run
- failure information

### `ar_source_signals`

Canonical external content object.

Identity:

```text
(source_platform, external_content_id)
```

A Threads post seen repeatedly by different searches remains one Source Signal.

Stored fields intentionally stay minimal:
- external content id
- permalink
- public author handle
- text
- media type
- published time
- content hash
- adapter version
- quote-post flag
- first/last observed time

No user ownership is attached to Source Signals.

### `ar_source_signal_observations`

Records that one Source Signal was observed in one ingestion run.

This is intentionally separate from `ar_source_signals` so query/cadence provenance survives deduplication and can later support defensible trend calculations.

## Security boundary

All three source tables:
- have RLS enabled
- expose no anon/authenticated policies
- revoke table access from `public`, `anon`, and `authenticated`
- are accessed only by server-side service-role code

The ingestion endpoint additionally requires `requireRadarCurator()`.

## Curator Source Lab

Route:

```text
/curator/sources
```

Functions:
- show whether a Threads server token is configured
- execute curator-only Threads search
- show fetched/new/duplicate/skipped counts
- show normalized signals returned by the run
- show recent ingestion runs
- show recent persisted Source Signals

The UI never receives the Threads access token.

## Environment

```text
THREADS_ACCESS_TOKEN=<server-only token with threads_keyword_search>
THREADS_API_HOST=https://graph.threads.net   # optional override
```

`THREADS_ACCESS_TOKEN` must not use a `NEXT_PUBLIC_` prefix.

## Dedupe behavior

1. Normalize fetched Threads posts.
2. Skip records without both `id` and non-empty `text`.
3. Collapse duplicate external ids inside the same response.
4. Upsert by `(source_platform, external_content_id)`.
5. Record a separate Observation for this run.
6. Update `last_seen_at` without changing canonical identity.

`content_hash` is retained as a secondary diagnostic/dedupe signal, not as primary identity.

## Explicit non-goals

Phase 15.4 does not implement:
- complaint relevance classification
- spam/ad/repost filtering
- LLM Evidence extraction from Source Signals
- Problem clustering
- automatic Public Problem creation
- recurring monitoring/schedules
- pagination crawling across arbitrary depth
- Trend labels
- X/Instagram/Facebook adapters

## Deployment policy

`vercel.json` remains:

```json
{
  "git": {
    "deploymentEnabled": false
  }
}
```

Therefore Phase 15.4 may merge to `main` without automatic Vercel deployment. Deployment stays paused until a later phase explicitly requires deployed-environment verification.

## Validation boundary

CI can validate:
- search input normalization
- official endpoint/parameter construction
- server-only bearer authorization
- deterministic Threads → Source Signal normalization
- missing-token fail-closed behavior
- DB contract
- curator-only route contract
- build/runtime regressions

CI cannot prove a live Threads search succeeds because repository CI intentionally has no production Threads credential.

The first live external call therefore remains a credential-dependent operational check after a valid Meta Threads app/token with `threads_keyword_search` is configured.
